# REST homework — scenarios and routing resources

The [advanced REST extension](REST-ADVANCED.md) adds Flyway schema management, customer links, and canonical `/api/v1/...` routes. The unversioned routes shown below remain working compatibility aliases.

## Domain model

`Scenario` has a generated ID, a nonblank name (maximum 100 characters), and sets of vehicles and deliveries. It owns two unidirectional `@ManyToMany` associations through `scenario_vehicles` and `scenario_deliveries`. Each join table has a composite primary key so membership cannot be duplicated. The same vehicle or delivery may belong to several scenarios.

No persist/remove cascades apply to shared resources. Deleting a scenario removes its memberships and preserves its vehicles, deliveries, customers, depot, and drivers. Deleting a vehicle or delivery that is still selected in a scenario returns `409 Conflict`; remove its memberships first. Deleting a customer with deliveries also returns `409`.

Scenario PUT replaces its complete name and membership sets atomically. Missing referenced IDs return `404` and preserve the previous state. Empty membership sets are valid for a scenario being prepared. Scenarios do not yet generate routing solutions.

## Database setup

- Fresh PostgreSQL database: Flyway automatically applies V1 and V2 on startup.
- Existing manually created database: use the explicit baseline procedure in [REST-ADVANCED.md](REST-ADVANCED.md#adopt-an-existing-manually-created-database). Do not rerun manual creation scripts.
- H2 tests: Flyway runs the same migration files; Hibernate validates the result.

The normal application continues to use `ddl-auto: validate` and the existing `DB_URL`, `DB_USERNAME`, and `DB_PASSWORD` environment variables.

## CRUD endpoints

All four resources use the same operations:

| Operation | Method and path | Successful response |
| --- | --- | --- |
| Create | `POST /api/{resource}` | `201`, DTO body and `Location` header |
| List | `GET /api/{resource}` | `200`, DTO array, including `[]` when empty |
| Read | `GET /api/{resource}/{id}` | `200`, DTO body |
| Replace | `PUT /api/{resource}/{id}` | `200`, updated DTO body |
| Delete | `DELETE /api/{resource}/{id}` | `204`, no body |

Resources are `customers`, `vehicles`, `deliveries`, and `scenarios`. PUT requires an existing ID. IDs are generated by the server. DTOs expose association IDs instead of serializing JPA relationships; lazy scenario membership is mapped inside the service transaction.

Example request bodies (replace reference IDs with actual IDs in your database):

```json
{
  "name": "Van 1",
  "capacity": 1000,
  "depotId": 1,
  "available": true
}
```

```json
{
  "customerId": 1,
  "quantity": 25.5,
  "notes": "Fragile",
  "timestamp": "2026-11-02T10:00:00Z"
}
```

```json
{
  "name": "Morning scenario",
  "vehicleIds": [1, 2],
  "deliveryIds": [1, 2, 3]
}
```

Vehicle requests require name, positive capacity (maximum nine integer and three fractional digits), an existing positive `depotId`, and a boolean `available`. The depot is explicit so the earlier multi-depot model remains usable; for this homework, use the single existing depot's ID (`SELECT id, name FROM depots`). This API creates vehicles without drivers. It preserves the earlier driver services and rejects edits of a vehicle with an assigned driver until that driver is unassigned.

Delivery requests require an existing positive `customerId`, positive quantity (maximum nine integer and three fractional digits), and an ISO-8601 timestamp with an offset. Notes are optional. Customer request fields are described in [README.md](README.md#customer-rest-api).

Scenario requests require a nonblank name and both ID sets; IDs must be nonnull and positive. Bean Validation runs through `@Valid` on request DTOs. Malformed JSON/XML or invalid values return `400`. `ResourceNotFoundException` (and its customer subclass) and `ApiConflictException` are custom runtime exceptions handled globally by `ApiExceptionHandler`. Missing resources return `404`; data integrity conflicts return `409`. Errors use Spring `ProblemDetail`, and validation responses include field errors without exposing database exception details.

## Conditional GET and JSON/XML

Successful GET responses for every API resource and list include an `ETag`. The filter calculates a weak validator from the serialized response bytes and includes `Vary: Accept`. Matching `If-None-Match` values return `304` with an ETag and no body. It supports individual validators, comma-separated validators, weak/strong comparisons, and `*` for an existing resource. A missing resource still returns `404`, even with `If-None-Match: *`.

Changing the returned data changes its validator. JSON and XML use separate validators because their response bytes differ. This saves response bandwidth; it still queries and serializes the resource. It does not implement optimistic locking for writes.

```sh
curl -i -H 'Accept: application/json' http://localhost:8080/api/scenarios/1
# Copy the exact ETag from the previous response:
curl -i -H 'Accept: application/json' \
  -H 'If-None-Match: W/"replace-with-returned-hash"' \
  http://localhost:8080/api/scenarios/1
curl -i -H 'Accept: application/xml' http://localhost:8080/api/scenarios/1
```

XML responses are supported for all resources through Jackson XML. Vehicle XML request example:

```sh
curl -i -X POST http://localhost:8080/api/vehicles \
  -H 'Content-Type: application/xml' -H 'Accept: application/xml' \
  -d '<VehicleRequest><name>XML van</name><capacity>50</capacity><depotId>1</depotId><available>true</available></VehicleRequest>'
```

## Run and verify

Run `./mvnw test` for the integration suite. It checks separate HTTP requests, shared memberships, replacement and deletion behavior, validation, failed-update rollback, conditional JSON/XML GETs, XML requests, and generated OpenAPI documentation, alongside the earlier lab tests.

To run a disposable H2 server with one depot (ID 1), without PostgreSQL credentials:

```sh
./mvnw spring-boot:test-run \
  -Dspring-boot.run.profiles=test,api-demo \
  -Dspring-boot.run.jvmArguments=-Dspring.devtools.restart.enabled=false \
  -Dspring-boot.run.arguments=--server.port=18080
```

In another terminal:

```sh
python3 scripts/test-customers.py http://localhost:18080
python3 scripts/test-routing-api.py http://localhost:18080 1
```

The second argument to the routing script is an existing depot ID. Both scripts execute real curl requests, assert status codes and response contents, and clean up their own records. The routing script also checks shared membership, deletion conflicts, changed ETags, `304` with empty bodies, and XML responses. The optional demo depot remains until the in-memory server shuts down.

## Swagger UI

Open `http://localhost:18080/swagger-ui/index.html` (or port 8080 for the normal server). The OpenAPI document is at `/v3/api-docs`.

`GET /api/scenarios/{id}` has explicit Springdoc annotations documenting its description, optional `If-None-Match` header, successful response with ETag, `304`, and `404`. Create and delete operations document `201` and `204`.

1. Expand `POST /api/scenarios`, click **Try it out**, choose JSON, and enter `{"name":"Swagger demo","vehicleIds":[],"deliveryIds":[]}`.
2. Click **Execute** and verify `201` plus a `Location` header. Record the returned ID.
3. Expand `GET /api/scenarios/{id}`, click **Try it out**, enter the ID, and execute. Verify `200` and the scenario data; copy its ETag.
4. Enter that ETag in `If-None-Match` and execute again. Verify `304` and an empty response body.
5. Choose `application/xml` as the response media type, clear `If-None-Match`, and execute again to inspect XML.

The implementation was also exercised through the real Swagger UI: creating an empty scenario returned `201` with XML negotiated from a JSON request, and reading the documented endpoint returned `200`, JSON data, and an ETag. Sending that ETag through the documented `If-None-Match` field returned `304` with no body. The final build also returned the correctly documented `201` for a JSON scenario creation.
